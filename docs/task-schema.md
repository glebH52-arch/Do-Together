# Расширение задач: совместимый первый шаг

Миграция `000005` не меняет существующие числовые ID пользователей, проектов, приглашений и задач. Их продолжают использовать JWT, Redis refresh-сессии и текущие HTTP-маршруты. Задача дополнительно получает UUID; клиент может перейти на него отдельным совместимым шагом. Старые задачи и связи сохраняются.

Ключ задачи имеет вид `DOT-<project_id>-<number>`. `project_id` — стабильная часть префикса, поэтому переименование проекта не меняет выданные ключи. Номер выделяется обновлением строки проекта; создание задачи и запись события `created` входят в тот же SQL-запрос и PostgreSQL-транзакцию. Уникальность UUID, ключа и пары `(project_id, task_number)` обеспечивают ограничения БД.

Старые задачи получают номера в порядке прежнего числового ID внутри проекта. Для задач `done` `completed_at` заполняется из `updated_at` либо `created_at`. Исходные задачи, проекты и приглашения не удаляются.

Изменение задачи и событие истории выполняются в одной транзакции. Условие на прежний `status` и `updated_at` не даёт устаревшему запросу тихо перезаписать конкурирующее изменение; он получает конфликт. Если запись истории падает, изменение задачи откатывается. Фактический no-op не создаёт событие.

Список задач получает имя автора и исполнителя одним запросом через `JOIN`, без запроса на каждую задачу.

`GET /projects/{id}/board` возвращает массивы `todo`, `in_progress`, `review`, `done`, включая пустые. `PATCH /projects/{id}/tasks/{taskID}/position` принимает `expected_status`, `expected_position` и `before_task_id` (`null` означает конец колонки). Перемещение допускается только внутри текущей колонки. Строка проекта блокируется на время расчёта позиции; повторный запрос со старой позицией получает `409`. Между задачами сохраняются промежутки в позициях, а когда промежуток исчерпан, колонка перенумеровывается в той же транзакции.

Комментарии доступны по `/projects/{id}/tasks/{taskID}/comments` (`GET` с `limit`/`offset` и `POST`) и `/projects/{id}/tasks/{taskID}/comments/{commentID}` (`PATCH`/`DELETE`). Читать и создавать может участник проекта; менять и удалять — только автор комментария, остающийся участником. Удаление комментария и событие истории входят в одну транзакцию.

`GET /projects/{id}/tasks/search` ищет по названию и описанию через PostgreSQL `ILIKE`. Доступны фильтры `status`, `assignee_id`, `priority`, `type`, `due_before`, `due_after`, а также `limit` (максимум 100), `offset`, `sort` и `direction`. Сортируются только разрешённые поля `created_at`, `due_at`, `title`, `priority`; числовой `id` используется для стабильного разрешения равных значений. Для текстового поиска созданы trigram-индексы, для основных фильтров — составной индекс. Проверка членства остаётся обязательной и при пустой выдаче.

`POST /projects/{id}/tasks` теперь принимает необязательные `type`, `priority`, `assignee_id`; отсутствие поля сохраняет прежние значения по умолчанию. `PATCH /projects/{id}/tasks/{taskID}` дополнительно принимает `type`, `priority`, `assignee_id`, `due_at`. Явный `null` у последних двух снимает назначение или срок. Исполнитель должен быть участником проекта. Значимые изменения записываются в историю по типу действия в той же транзакции; неизменённые поля события не создают.

SQL рабочих репозиториев хранится в `internal/repository/postgres/statement.go`; SQL внутри интеграционных тестов используется только для подготовки и проверки фикстур.

Проверка миграций выполнялась на отдельной копии существующей локальной БД. Рабочие Docker volumes не сбрасывались. Для интеграционного теста нужно задать `TEST_DATABASE_URL`, `TEST_PROJECT_ID` и `TEST_ACTOR_ID`, указывающие на одноразовую тестовую БД и участника проекта.
